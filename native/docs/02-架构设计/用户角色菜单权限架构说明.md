# 用户、角色、菜单与 API 权限架构

## 权限模型

系统使用数据库关系表实现 RBAC，并允许直接向用户授予 API 权限：

```text
用户 ── m_user_role ── 角色 ── m_role_menu ── 菜单
 │                       └── m_role_api_permission ── API 权限
 └── m_user_api_permission ──────────────────────── API 权限
```

- 菜单权限只通过角色授予，用户没有角色时没有菜单权限。
- API 权限可以通过角色授予，也可以直接授予用户，两者取并集。
- 启用且 `role_key = super_admin` 的角色拥有全部 API 权限。
- 禁用角色和禁用 API 权限不参与鉴权。
- API 权限支持精确资源、`*`、`user.*` 和 `*.read` 通配符，操作支持精确值和 `*`。

## 数据表

| 表 | 作用 |
| --- | --- |
| `s_user` | 用户 |
| `s_role` | 角色 |
| `s_menu` | 菜单 |
| `s_api_permission` | API 权限定义 |
| `m_user_role` | 用户与角色关系 |
| `m_role_menu` | 角色与菜单关系 |
| `m_role_api_permission` | 角色与 API 权限关系 |
| `m_user_api_permission` | 用户直接 API 权限关系 |

## API 鉴权流程

认证中间件解析 Token 并写入 `userId`。权限中间件随后调用数据库权限服务，按以下顺序判断：

1. 用户是否拥有启用的 `super_admin` 角色。
2. 用户启用角色所拥有的 API 权限是否匹配。
3. 用户直接拥有的 API 权限是否匹配。
4. 全部不匹配时返回 403。

权限关系写入数据库后立即生效，不需要同步策略或重载内存。

## 授权接口

- `GET /api/v1/role/:roleId/api-permissions`：查询角色的 API 权限。
- `POST /api/v1/role/:roleId/api-permissions`：覆盖角色的 API 权限。
- `GET /api/v1/user/:id/api-permissions`：查询用户直接 API 权限。
- `POST /api/v1/user/:id/api-permissions`：覆盖用户直接 API 权限。

角色分配菜单时，菜单关联的 API 权限也会同步到 `m_role_api_permission`。删除用户、角色或 API 权限时，会同时清理对应关系数据。

## 数据库迁移

应用启动时自动执行 Goose migration。迁移记录保存在 `goose_db_version`，迁移文件位于 `internal/database/migrations/sql/`。
